Part I

How the many-body grid follows the data

One sentence in the PR packs three mechanisms: every level divides the live data's bounding square, reduced on the GPU each tick and shifted by a random part of a cell so no cell boundary stays put. This page takes the sentence apart, texture by texture, with the shader code that does each step.

1 · Why the grid moved off the space

The many-body force is a Barnes-Hut style approximation. It lays a stack of square grids over the layout, sums every point into a cell on each grid, and lets a point feel far cells as single lumps of mass. Where the grids sit decides how many cells the layout actually gets to use.

On main every grid covered the fixed square [0, spaceSize]. A layout that fills a tenth of the space lands in a hundredth of the cells. Gravity pulls almost every layout well inside the space, so this was the normal case, not an edge case: 10k points settle about 1,270 units wide inside a 4,096 square.

The measured cost of the old placement, at 100k points with the finest grid at 512² and 8 near-field sampling slots, against an exact float64 all-pairs force:

layout side / space sidepoints per finest cell, mainerror, mainerror, this PR
1.00.380.060 %0.091 %
0.256.100.354 %0.089 %
0.138.11.840 %0.090 %

Flat in the layout's size, because the grid no longer knows where the layout sits in the space. The rest of this page is how that is done without ever reading a position back to the CPU.

2 · Reducing the bounding square on the GPU

To fit the grid, the engine needs min and max of every live position, every tick. A readback would stall the pipeline, so the reduction runs as three full-screen fragment passes, each writing a smaller texture, until one texel is left. That texel is then read by the shaders that bin points. It lives in src/modules/Shared/data-bounds.ts.

Pass 1: partial boxes with a stride

Fragment b of the buckets texture does not take a tile of the positions texture. It strides through the point list: points b, b + 64², b + 2·64², and so on. The work splits evenly whatever order the points were uploaded in and wherever they sit in space. A fragment skips absent points and non-finite positions, so one NaN cannot set the grid size for the whole graph.

src/modules/Shared/reduce-bounds-buckets.frag 
out vec4 bounds; // [minX, minY, maxX, maxY]

bool isUsable(vec2 position) {
  // Exponent bits all set = Inf or NaN. Read the bits rather than compare:
  // a fast-math compiler may fold `x != x` away.
  uvec2 exponent = floatBitsToUint(position) & 0x7f800000u;
  if (any(equal(exponent, uvec2(0x7f800000u)))) return false;
  return all(lessThanEqual(abs(position), vec2(BOUNDS_LIMIT)));
}

void main() {
  ivec2 bucket = ivec2(gl_FragCoord.xy);
  int stride = buckets * buckets;          // 64² = 4096

  vec2 lo = vec2(BOUNDS_LIMIT);             // an empty bucket stays neutral
  vec2 hi = vec2(-BOUNDS_LIMIT);

  for (int i = bucket.y * buckets + bucket.x; i < count; i += stride) {
    ivec2 texel = ivec2(i % size, i / size);
    if (texelFetch(exitTexture, texel, 0).g > 0.5) continue;   // absent point
    vec2 position = texelFetch(positionsTexture, texel, 0).rg;
    if (!isUsable(position)) continue;
    lo = min(lo, position);
    hi = max(hi, position);
  }
  bounds = vec4(lo, hi);
}

Why a stride and not a tile

Any split of the point list gives the same final box, bit for bit, because min and max are exact and order-independent. So the split is chosen for cost alone. The obvious alternative is a tile: fragment b takes a contiguous run of k = ⌈N / 4096⌉ points. Both have the same longest loop. The difference is what the GPU reads on each loop iteration.

A GPU does not run fragments one at a time. It runs neighbouring fragments in lockstep groups, 32 on NVIDIA and Apple, 32 or 64 on AMD, and texture reads go through a cache of neighbouring texels. On iteration j the group of fragments b, b+1, b+2, … reads:

This is the standard GPU reduction pattern, not a cosmos invention. Mark Harris's NVIDIA deck Optimizing Parallel Reduction in CUDA (2007) arrives at it as its final kernel: each thread first sums many elements in a loop whose step is the whole grid's size, annotated on slide 33 as "gridSize loop stride to maintain coalescing!", and only then does the tree reduction. That kernel ran 30 times faster than the first version on the same GPU, and slide 37 attributes most of it to addressing and this cascading, not to loop unrolling. His 2013 post Write Flexible Kernels with Grid-Stride Loops names the pattern and states the reason in one sentence: "By using a loop with stride equal to the grid size, we ensure that all addressing within warps is unit-stride, so we get maximum memory coalescing." NVIDIA's Best Practices Guide has the measurement behind it: effective bandwidth falls as the stride between neighbouring threads grows, until every thread pays for its own memory transaction.

Those sources are about CUDA threads and global memory. The same mechanics hold for a fragment shader: fragments are dispatched in the same lockstep groups (Fabian Giesen's A trip through the Graphics Pipeline, part 8 describes the 32-thread warp of 2 × 2 pixel quads), and texelFetch goes through the texture cache. Adjacent fragments reading adjacent texels is the fragment-shader form of a coalesced load.

The cosmos reduction mirrors Harris's shape pass for pass. His "algorithm cascading", each thread folding many elements sequentially before any tree step, is pass 1 folding about 64 points per fragment (POINTS_PER_BUCKET). His kernel launches as the only global synchronisation are the three render passes here. He found 1,024 to 4,096 elements per thread best on a 2007 GPU; cosmos settled on about 64 by measuring the pass on an M3 Max, where fewer points per fragment and more fragments won. Two smaller things the stride gives for free: the loop is a single bound, i < count, with no chunk size or remainder to handle, and every fragment gets either k or k − 1 points, so none sits idle while another holds the leftover.

Pass 2: fold 8 × 8 blocks

This pass exists for one reason: folding all 4,096 partial boxes in a single fragment cost about 0.75 ms per tick on an M3 Max, 11 % of a 100k-point step. With a middle pass the whole reduction costs about 0.16 ms. Each fragment reads an 8 × 8 block of the buckets texture and writes its min and max.

src/modules/Shared/reduce-bounds-blocks.frag 
ivec2 first = ivec2(gl_FragCoord.xy) * size;        // size = 8
for (int y = 0; y < size; y += 1) {
  for (int x = 0; x < size; x += 1) {
    vec4 partial = texelFetch(partialsTexture, first + ivec2(x, y), 0);
    lo = min(lo, partial.xy);
    hi = max(hi, partial.zw);
  }
}
bounds = vec4(lo, hi);

Pass 3: one texel, made square

The last fragment folds the 8 × 8 blocks texture and turns the rectangle into the texel the consumers want. Three things happen to it here. It becomes a square around the data's centre, because the levels halve exactly and non-square cells would break that. It is floored at a minimum extent, so one point or a coincident stack still yields a usable cell. And it is optionally padded and shifted, which is section 6. The reciprocal is computed here, once, so every shader multiplies by the same bits instead of dividing on its own.

src/modules/Shared/reduce-bounds-final.frag 
// ... fold the blocks texture into lo / hi as in pass 2 ...

if (hi.x < lo.x) { lo = vec2(0.0); hi = vec2(0.0); }   // no usable point at all

vec2 centre = 0.5 * (lo + hi);
float span = max(hi.x - lo.x, hi.y - lo.y);          // square: the larger side
float extent = max(span, minExtent);                 // floor: ¼ unit per finest cell
vec2 origin = centre - 0.5 * extent;

// Origin shift (section 6): pad by one coarsest cell, slide back by a part of it.
if (shiftCellsPerAxis > 1.0) {
  float cell = extent / (shiftCellsPerAxis - 1.0);   // 8 cells over the padded box → 1/7 of the fitted side
  origin -= vec2(shiftOffsetX, shiftOffsetY) * cell;
  extent += cell;
}

bounds = vec4(origin, extent, 1.0 / extent);        // [originX, originY, extent, 1/extent]

3 · One cell formula, four shaders

A level is an N × N grid of square cells laid over the data square from pass 3. Everything the pyramid does starts with one question: given a world position, which cell is it in? The answer is a pair of integers, column and row. Four shaders ask it, and they ask it from two sides:

shaderasks aboutside
calculate-level.vertpoint Q, to add it into a level's cell sumfiling
build-nearfield-slots.vertpoint Q, to write it into a finest-cell slotfiling
force-level.fragpoint P, to pick which cells to read and which 3 × 3 to skiplooking up
force-nearfield.fragpoint P, to pick which 3 × 3 of slots to readlooking up

The filing side puts each point's mass into a drawer. The looking-up side opens drawers around P. The force comes out right only if a point filed into drawer 5 is also found when the lookup opens drawer 5, and nowhere else. Section 4 shows how the lookup divides the plane into rings so that each point is read exactly once. Here the point is simpler: the two sides must name the same drawer for the same position.

The cure is boring on purpose: one formula, written once in grid-cell.ts, pasted into all four shaders at a // @grid-cell marker, so the source text is identical. Identical text is not enough on its own, because the four are separately compiled programs. The GLSL ES spec lets a compiler implement division slightly inexactly, by up to 2.5 units in the last decimal place, and two compilers may choose differently. Subtraction and multiplication, by contrast, must be correctly rounded: same inputs, same bits, in every program. So the formula uses only those two, and the one division it needs, 1/extent, was done once in pass 3 and travels in the texel.

src/modules/ForceManyBody/grid-cell.ts (the GLSL that gets spliced in) 
uniform highp sampler2D dataBoundsTexture;   // the 1×1 texel from pass 3

ivec2 gridCell(vec2 worldPosition, float cellsPerAxis) {
  vec4 dataBox = texelFetch(dataBoundsTexture, ivec2(0), 0);          // 1. read [originX, originY, extent, 1/extent]
  float cellsPerUnit = dataBox.w * cellsPerAxis;                   // 2. cells per world unit = (1/extent) × N
  ivec2 lastCell = ivec2(int(cellsPerAxis) - 1);
  return clamp(ivec2(floor((worldPosition - dataBox.xy) * cellsPerUnit)),  // 3. offset from corner, 4. scale, 5. floor
               ivec2(0), lastCell);                                   // 6. outside the box → edge cell
}

In words: measure how far the point is from the box's lower-left corner, multiply by how many cells fit in one world unit, and drop the fraction. A point left of or below the box gets cell 0, one past the far edge gets the last cell. The multiplication in step 2 is also exact: N is a power of two, and multiplying a float by a power of two changes only its exponent.

Worked through with numbers. Say the texel holds origin (940, 1840) and extent 1600, so 1/extent = 0.000625. A point at (1360, 2900):

levelcellsPerUnit(p − origin) · cellsPerUnitcell
8²0.005(420, 1060) · 0.005 = (2.10, 5.30)(2, 5)
16²0.01(4.20, 10.60)(4, 10) = 2·(2, 5)
32²0.02(8.40, 21.20)(8, 21) = 2·(4, 10) + (0, 1)

Read the last column downward. Each level's cell is twice the previous one's, or twice plus one. That is the parent–child relation: a cell on one level splits into exactly four on the next, and a point in the parent is always in one of those four children.

Section 4 leans on this relation. On each finer level the force shader reads the children of the 3 × 3 block it skipped on the coarser level, a 6 × 6 block, and skips its own 3 × 3 inside it. That only lines up if "the children of my parent's neighbours" are exactly the cells the formula produces one level down, which the exact doubling guarantees. Since c30843e the coarse levels skip 5 × 5 and read 10 × 10 child blocks; the relation is the same, with 2·r in place of the fixed 2.

4 · The pyramid textures

A level is a plain 2D texture with one texel per cell. Every tick each point is drawn into every level as a 1-pixel point sprite with additive blending, so a texel accumulates [Σx, Σy, count, 0] over the points in its cell. The cell's centre of mass is Σ / count, computed by whoever reads it.

src/modules/ForceManyBody/calculate-level.vert 
vec4 pointPosition = texelFetch(positionsTexture, pointTexel, 0);
vColor = vec4(pointPosition.rg, 1.0, 0.0);              // what additive blending sums: [x, y, 1, 0]

ivec2 cell = gridCell(pointPosition.rg, levelGridSize);  // the shared formula

vec2 levelPosition = 2.0 * (vec2(cell) + 0.5) / levelGridSize - 1.0;   // cell centre in NDC
gl_Position = vec4(levelPosition, 0.0, 1.0);
gl_PointSize = 1.0;                                     // one fragment, one texel

The force shader walks the texture accordingly. The coarsest level loops over the whole grid minus the 3 × 3 shell; every finer level loops over the 6 × 6 child block of the coarser shell minus its own 3 × 3. The base of that 6 × 6 block is where the parent-child relation from section 3 is needed: (pointCell / 2) * 2 - 2 is only the right corner if this level's cell really is 2·parent or 2·parent + 1.

Since c30843e (21 October) the shell is per level. Every level but the finest leaves a 5 × 5 shell, radius 2, and the next level refines it as a 10 × 10 block, (4r+2)² cells from (pointCell / 2) * 2 - 2·r; the finest keeps 3 × 3 for the near field. A centroid is then only used from two cells away, where its error is about a quarter. The shader takes the level's own radius and its parent's as two uniforms, shellRadius and parentShellRadius, and getShellRadius in index.ts is the one place the rule lives. The listing below is the branch at 08b58ed, before that change; the figure above keeps its 3 × 3 and 6 × 6 for the same reason.       if (max(cellDist.x, cellDist.y) <= 1) continue;        // own 3×3: next level, or near field

    }
}

5 · Why a fixed grid draws a cross

Exactly-once coverage says every cell is charged to one pass. It says nothing about what happens when a point moves. The set of cells a level treats as centroids is chosen relative to the point's own cell, so when the point steps across a cell boundary the whole 3 × 3 shell moves with it. One column of cells switches from "one centroid here" to "refined by finer levels", and the column on the other side switches back. The two treatments approximate the same mass slightly differently, so the force jumps at the boundary.

The centre lines dip deepest. A crossing there switches a column of coarsest cells on both sides of the point, while near the box's edge the 3 × 3 shell is clipped and only one column switches. In a 300k-point layout the density in a thin strip along a centre line, divided by the density around it:

gridcentre linesquarter linesoff-boundary lines
main, on the space (spaceSize 8192)0.791.001.00
on the data, fixed, from 4²0.870.971.00
on the data, fixed, from 8²0.990.981.00
on the data, shifted every tick, from 8²1.011.001.00

main drew the same cross, along the centre lines of the space. Fitting the grid to the data had only moved it to the layout's centre, where it is far more visible.

6 · The per-tick shift

If the boundaries cannot be made continuous, they can be made to move. Every tick, pass 3 pads the fitted square by one cell of the coarsest grid and slides the origin back by a random fraction of that cell on each axis. With 8 cells over the padded box, one cell is a seventh of the fitted side. The padding equals the slide's full range, so the data stays inside whatever the draw.

A uniform random shift over one coarsest cell is uniform modulo every finer cell as well, since finer cells divide the coarse one exactly. So over many ticks every level's boundaries land evenly everywhere, the jumps average into a continuous force, and what is left is per-tick noise that alpha anneals.

That noise was small on the uniform layouts the author measured and visible on clustered ones: in the Lasso Selection story every point shook. The shift moves the jumps without shrinking them, and on clustered data a coarse cell's centroid stands for very uneven mass. c30843e shrank the jumps by widening the shell to 5 × 5 above the finest level, as section 4 notes; the shift itself is unchanged. The experiments that led there, and the three recordings, are on Part II.

The orange band is the padding, one coarsest cell wide. The grid's origin sits somewhere inside it, decided by the two offsets. The fitted square never leaves the grid.

The engine side is small. The force asks DataBounds for the shift each tick with two uniform draws from the simulation's random stream, which randomSeed seeds when set. That is also why two copies of the same blob at different places now get the same grid: the shift is relative to the data, not to the space.

Three decisions sit behind the numbers, each measured rather than assumed.

decisionwhy
Pad only together with the shiftA fixed margin leaves the layout's edge mid-cell on every level and buys nothing: 0.124 % vs 0.060 % error on a square. The shift needs the padding and pays for it by removing the seams.
Start the pyramid at 8², not 4²From 4² the padding would be a third of the box, not a seventh. The 4² pass was also the slowest (a sixteenth of all points blends into each texel) and the least accurate. Dropping it took about 30 % off a step at 100k to 300k points.
Floor the box at ¼ unit per finest cellOnly has to keep a single point or a coincident stack indexable. At 1 unit it bound at ordinary densities and raised the error of a tenth-of-the-space square from 0.06 % to 0.30 %.

What the shift costs: a little accuracy per tick, since the layout's edge now falls mid-cell (0.091 % per tick instead of 0.055 % on a square, 0.066 % for the 20-tick mean), about 6 % of a step because occupied cells hold roughly 1.3 times the points, and a per-tick motion of 0.0023 point spacings at a 300k equilibrium with alpha held at 1, against 0.001 without. All of it anneals with alpha.

7 · The whole tick

The order matters. The bounds run first and once, because every later pass bins against the box they define, this tick's shift included. If the aggregation and the force binned against different boxes the exactly-once coverage would break.

8 · What spaceSize still does, and how to retire it

With the wall gone, spaceSize has no geometric meaning left. It is one number doing six unrelated jobs that happen to share a value, plus a coordinate offset that exists only because v1 put the origin in the corner of a texture. This is every live use on the branch, from a grep of src/:

The target

Positions are plain numbers with the origin at (0, 0). The force kernel's own unit, where distanceMin is 1 and the finest cell is at least a quarter, is the only scale the engine knows. Each job becomes:

jobreplacement
world origin(0, 0). Delete worldOrigin and the subtraction in every draw and pick shader. Screen centre at zoom 1 shows the origin.
initial layout sizeA size from the point count, about k · √n world units, as one named constant with its measured rationale.
per-force step capA named constant in world units, large enough to be only a non-finite guard. It was never tuned.
many-body kick capThe same formula with a named constant in place of spaceSize, so the value is unchanged at the default and the dependence on n stays.
±Infinity inputTreat as absent with a warning, or map to the origin. Bad input should not inherit a magic edge.
precision warningWarn at ingest when a position's magnitude exceeds 2²⁰, the same check applied to what actually matters.

The migration for users is one sentence: positions saved under the old convention are centred on 2,048, so subtract 2,048 from x and y once, or keep the data and pan. Nothing else in the public API moves, and the defaults keep layouts looking the same.

Staging

  1. Now, non-breaking. Give the four internal constants their own names and let spaceSize feed only the origin and the initial scale. Bit-identical at the default, a pure refactor, reviewable on its own.
  2. Next major. Delete the config key and the origin subtraction, add the one-sentence migration-notes entry. By then the diff is one key and one uniform, which downstream apps that pass the key through can absorb in one release.
  3. Separately, with readings. If the initial layout size or the kick cap is to be derived from n or from the kernel unit rather than copied from the old default, that is a tuning change. It gets its own PR with before-and-after measurements, the way the 8² coarsest level and the 64-point bucket were done.

Why not a rename. A key called worldSize or worldOrigin would preserve the coupling under a truer name. The point of removing it is that the six jobs stop sharing a value they have no reason to share.

The audit added a seventh job, the deck-layers package's default placement and view-transform probe, and a fourth rescale number, the "no rescale above a range of S" cutoff. The posted plan is in two steps: name the values and deprecate the key now, identical for every graph; then the origin to (0, 0) and the key removed, breaking, with the author choosing whether that second step lands in this PR or in the next major. It also says plainly that the 4,096-unit reference length survives in the constants until a separate, measured retune. Step one landed on 22 October as ca739de: the values are named on Store (worldOrigin, referenceLength, stepGuard, kickSpan, infiniteInputEdge), the rescale and the deck layer read them, and a non-default spaceSize logs the deprecation. Part II · commit c30843e

Why the far field keeps two cells away

The branch let the many-body grid follow the data. On it, a clustered layout shook. The grid moved a little every tick to erase a cross. That meant its cell boundaries, and the small force jump at each of them, swept over every point every tick, and the jump became visible motion. This part is the long version of the fix comment. It shows where the jump comes from, what the level textures look like around a point, what each experiment showed, and what the fix costs.

What was seen
A clustered 22,500-point layout shook on the branch and was still on main. A uniform 300k blob was still on both.
What was done
One rule in the far-field shader changed. Each level used to sum every cell as one lump, except the 3 × 3 block around the point. That block went to the next, finer level. Now every level but the finest hands down a 5 × 5 block instead. Commit c30843e: one shader loop and one function, plus docs.
Why it works
The force jumps when a point crosses a cell boundary. The cells just outside its block swap between "one lump" and "refined", and the jump is the lump's error. That error falls as 1/d³ with distance. A 5 × 5 block moves the nearest lump from two cells away to three, which halves the jump. The grid's per-tick shift had been turning the jump into motion. The shift stays, and now has half as much to spread.
What it costs
About a third more time per step from 50,000 points up. Two percent at 20,000, four at 16,000, nothing at 5,000 and below. Motion at rest fell from 0.0181 to 0.0082 point spacings per tick. main sits at 0.0137. That cost is why the shell later became a setting with a size-tiered default, simulationRepulsionQuality; the afterword has the numbers.

Words used in this part

level
one grid of the pyramid over the data's square: 8², 16², … up to about 2·√n cells per axis. Each is a texture with one texel per cell.
texel
one cell's record: the sum of x, the sum of y and the count of the points inside it.
lump, centroid
treating all of a cell's points as one mass at their average position. Cheap: one texel read. Wrong by an amount that falls with distance.
boundary
the line between two neighbouring cells of a level. A point crossing one changes its cell index by one. Every coarse boundary is also a boundary of every finer level. When the grid shifts, every boundary moves with it.
shell
the block of cells around the point's own cell that a level does not sum, and hands to the next level. 3 × 3 before, 5 × 5 now above the finest level. The author's word; it is a solid block, not a ring.
block
on the next level, the children of the shell above: 6 × 6 cells before, 10 × 10 now. A level sums its block minus its own shell.
near field
the finest level's 3 × 3, handled by a separate pass with real points, no lumps.
shift
the grid's origin moves by a random fraction of a coarsest cell every tick, so no cell boundary stays on one line.

2 · How a level builds the force, and what its texture holds

The far field is a stack of grids over the data's square: 8², 16², 32², up to about 2·√n cells per axis. Each grid is a texture. Each texel holds the sum of positions and the count of the points in its cell, so a centroid can be formed. The force on a point P is built level by level. A level sums the cells it is responsible for as centroids. It leaves a block of cells around P's own cell, the shell, to the next finer level. That level splits each of those cells into four. One picture of the whole scheme first, then the real textures.

The demo below builds the level textures of a clustered layout like the Lasso story's: 22,500 points in 25 clusters, levels 8² to 256². The engine would go to 512² for this count; the page stops one level short so the texels stay visible. Each texel's count is drawn as a tile in the page's text colour. More points make a more solid tile. An empty cell has no tile and shows only its colour. Pick a level and a shell radius, and click to move P. Teal cells are summed as centroids on this level. Orange cells are the shell, handed down. The near field exists on the finest level only, 256² here. Select it and the shell turns purple: the 3 × 3 block where real points are used instead of centroids. Those cells are under two pixels wide here, so the shell, the refined block and the near field are outlined on every level. At 256² an inset in the corner magnifies the cells around P.

Three things to look for. The orange shell is a solid block, not a ring. It includes P's own cell. On every level but the coarsest, the teal cells form a frame around the shell. What each colour does to the force on P

  • The tile is the texel's count: how many points fell into that cell on this level. It is drawn in the page's text colour, faint for a few points and solid for many. An empty cell has no tile. The colour and the tile answer two different questions. The colour says whether the shader reads the cell on this level. The tile says whether there is any mass in it to push with. An empty teal cell is still read, which costs one texel fetch, and the shader adds no force for it. The texel also holds the summed x and y of its points. Divided by the count, that is the centroid.
  • Teal cells push P on this level, each as one lump. The push is proportional to the count, points away from the centroid, and falls off as 1/d. One texel read per cell. These cells are far enough away for a centroid to stand in for their points. How far is the shell radius: one cell before the fix, two after.
  • Orange cells add nothing on this level. They are too close for a lump. They go to the next level, where each becomes four smaller cells and the same decision is made again. When P crosses a cell boundary, this block moves with it. The cells that enter or leave it swap between "one lump now" and "four lumps on the next level". The difference between those two is the jump.
  • Purple appears on the finest level only. Its nine cells hold the points that push P one by one, through the near-field pass with its sampling slots. No centroid at all. This is the only part of the force where close points repel each other individually. It is what keeps dense hubs from collapsing into disks.

Across the whole pyramid, every cell of the plane plays one of these roles for P on exactly one level. It is summed as a lump somewhere, or it is inside the finest near field. That is the exact-once decomposition. The all-levels view below shows it.

Follow one point

The small square in every view is one more point, Q, a little over one coarse cell from P. On each level its cell is outlined in the colour of its role for P. Read the levels from coarse to fine. On the coarse levels Q sits inside P's shell: orange, not yet counted. On exactly one level it sits in a teal cell: counted there, as part of that cell's lump. On every finer level its cell lies outside P's block: already counted above, and not read again. That is the exact-once rule, for one point.

Now press the shift button. The grid moves by a random fraction of a coarsest cell, the way the engine moves it every tick. Q and P stay where they are, but the cell boundaries around them move, so the level that counts Q can change. When it changes, the force Q exerts on P changes from one lump's version to another, smaller lump's version, or the other way. That change is the jump. Press a few times and watch the counted level move up and down.

3 · Why the force jumps at a boundary, and why 5 × 5 halves the jump

The whole mechanism, in six steps.

  1. The shell follows P. Each level draws a block around P's own cell, the shell, and skips it. Everything outside the shell is counted as lumps. When P's cell changes, the shell slides with it.
  2. Cells change role at a boundary. When P crosses a cell boundary, or a boundary crosses P, the cells just outside the shell swap roles. One that was a single lump is now inside the shell, and the next level counts it as four smaller lumps. One on the other side goes from four small lumps to one big one.
  3. That is a step in the force. The points in those cells did not move. Only the counting changed. So the force on P steps between one tick and the next, by the difference between one lump and four. A true force would have changed by almost nothing in that time.
  4. The step is as big as a lump's error. A lump is a shortcut: one point standing in for many. It is wrong by more when the cell is close to P, and by more when its points are heaped to one side. Graph clusters are heaped. One cell away, which a 3 × 3 shell allows, is close.
  5. The shift turns the step into motion. The grid moves every tick, so a boundary passes over every point often. The step is felt everywhere, in bands, every tick. That is the jitter.
  6. The fix moves the shell out by one cell. The cells that change role are now one cell farther from P. There the same lump is about three tenths as wrong, and the step halves.

Step 2 in a picture:

Step 4: how wrong is a lump, and why distance fixes it

A lump puts all of a cell's points at their average position. A point on the near side of the cell really pushes P a bit harder than that; a point on the far side pushes a bit less. Because the average sits in the middle, those two errors nearly cancel. What is left is small and comes from the force law bending: 1/r is a curve, not a line, so the near side's extra push slightly outweighs the far side's shortfall. That leftover is the lump's error. It grows with how spread out the points are, and it shrinks with distance as 1/d³. In one line: a cell of width c at distance d, with mass m, pushes with about m/d and is wrong by about m·c²/d³.

Why 1/d³ and not 1/d: distance helps twice. The farther the cell, the smaller it looks from P, so the points inside it look more like one point; that is the (c/d)² part. And the farther the cell, the weaker its push to begin with; that is the 1/d part. Moving the nearest lump from two cell widths to three cuts its error to (2/3)³, about 0.3. The exponent is for this engine's 1/d repulsion; a 1/d² force would give 1/d⁴.

4 · Why moving the grid could not fix it

The size of the jump is set by the shell and by the data. How it looks on screen is set by how the grid moves. A fixed grid, the random shift the author added, and a slow drift tried during the investigation show the same jump three ways. Moving the boundaries changes when and where each point feels it. It never changes how big it is.

6 · The rule, and why it stays exact

Every level but the finest now leaves a shell of radius 2, the 5 × 5 block, to the next level. The finest level keeps radius 1. Its cells hold about one point each, so their centroids are the points themselves. A wider shell there would only make the near-field pass, the expensive one, cover 25 cells instead of 9, for nothing.

A level refines the shell its parent left as a block of children. A parent shell of radius r is 2r + 1 cells wide. Its children form a block 4r + 2 cells wide: 6 for radius 1, 10 for radius 2. The level sums that block minus its own shell. For every cell to be charged to exactly one pass, the level's own shell must lie inside the block it refines. Otherwise some cells would be handed down and never picked up.

7 · The code

The rule lives in one function. The shader receives a level's own radius and its parent's as two uniforms, and keeps one loop shape for every level.

src/modules/ForceManyBody/index.ts 
const getShellRadius = (level: number, levels: number): number => (level === levels - 1 ? 1 : 2)

// drawForces(), per level
shellRadius: getShellRadius(level, this.levels),
parentShellRadius: level === 0 ? 0 : getShellRadius(level - 1, this.levels),
src/modules/ForceManyBody/force-level.frag — the loop, before and after 
int shell = int(shellRadius);
if (isFirstLevel > 0.5) {
  // Coarsest level: every cell except the shell, which finer levels refine.
  for (int j = 0; j < gridSize; j += 1) for (int i = 0; i < gridSize; i += 1) {
    ivec2 cellDist = abs(ivec2(i, j) - pointCell);
    if (max(cellDist.x, cellDist.y) <= 1 shell) continue;
    velocity += cellVelocity(ivec2(i, j), position);
  }
} else {
  // The coarser level left its (2r+1)² shell; those cells refine to the aligned (4r+2)² child block.
  int parentShell = int(parentShellRadius);
  int blockSize = 2 * (2 * parentShell + 1);                 // 6 → 10
  ivec2 base = (pointCell / 2) * 2 - 2 2 * parentShell;       // -2 → -4
  for (int j = 0; j < 6 blockSize; j += 1) for (int i = 0; i < 6 blockSize; i += 1) {
    ivec2 cell = base + ivec2(i, j);
    if (any(lessThan(cell, ivec2(0))) || any(greaterThanEqual(cell, ivec2(gridSize)))) continue;
    ivec2 cellDist = abs(cell - pointCell);
    if (max(cellDist.x, cellDist.y) <= 1 shell) continue;
    velocity += cellVelocity(cell, position);
  }
}

Struck-through numbers are what the branch had. (pointCell / 2) * 2 is integer division followed by multiplication. It finds the first child of P's parent cell. That is why the cell index must double exactly from one level to the next; Part I, section 3 covers it.

9 · What remains

  • Faint ripples remain on clustered data with the 5 × 5 shell. Radius 2 cuts the jump at a boundary to about half, as section 3 works out. It does not remove it, and the random shift still spreads what is left. Radius 3 on the coarsest levels is the next dial, at 147 reads per level instead of 75. The structural alternative is a continuous weighting at the shell boundary, which the author's history entry lists as not tried. It would remove the jump rather than shrink it, at roughly the far-field cost the shell now has.
  • The harness error with the 5 × 5 shell is not measured. By construction it can only have fallen. More cells are refined, and nothing else moved.
  • The cost is a third of the step from 50,000 points up. The far-field passes are now a large share of the step, so any later saving there pays off directly.
  • The metric that would have told the partial variants apart from the full rule is coherence, not RMS. The Steady-State Motion story added in e40a649 reports both.

Afterword · commits e53aea7 and 1c4b884

The shell became a setting

Part II ends with the 5 × 5 shell on every level but the finest, for every graph, at a third of a step above 50,000 points. The same day the shell became a choice. simulationRepulsionQuality takes 'precise' for the 5 × 5 shell, 'fast' for the 3 × 3, and its default 'auto' is precise up to 25,000 points and fast above. The radius was already a per-level uniform, so the shader did not change; the setting is read every tick and applies to the next step.

Where the threshold comes from

Below about 25,000 points a step waits on the fixed cost of its render passes, some forty to sixty per tick and most of them near-field peeling, rather than on the far field's reads, so the wider shell's extra reads fill GPU time that was idle. From 30,000 up the far field is the largest part of the step and the extra shows in full. Repulsion Benchmark story, Chrome on an Apple M3, medians of five interleaved rounds, milliseconds per step:

2,000 points run the all-pairs path. 5,000 runs the grid with 32 near-field slots, which is why it is slower than 20,000 with 16: the step follows the pass count, not the point count, until the GPU work overtakes it. The crossover is one machine's; a slower GPU with the same CPU moves it lower.

Only the clustered layout changes by an amount the eye can see. The blob's threefold difference is far below a pixel, and the lattice's larger motion is the near field's and the collision's, the same under both shells. The jitter is also a hot-simulation effect: with the stock decay of 5,000 the clusters' 3 × 3 motion is 0.0260 at alpha 0.7, 0.0112 at 0.5, 0.0070 at 0.3 and 0.0024 at 0.1, so it falls below the 5 × 5 shell's held-alpha level once alpha passes about 0.3, which the default decay reaches after some 870 ticks, fifteen seconds at 60 fps. A layout that holds alpha high on clustered data sees it; a layout that settles does not. Below 25,000 points, where the wide shell is free, every graph keeps it; above, the fast shell is the default and the key opts in.

Tried and not taken

A rounded shell, the 5 × 5 minus its four corner cells, keeps every used centroid at least as far away as the axis-aligned cells the shell already keeps, still tiles exactly once, and cuts the far-field reads by 13 %. Measured over five interleaved rounds it saved 0.3, 0.34 and 0.59 ms at 50k, 100k and 200k points, 3 to 5 % of the step: the loop still walks the 10 × 10 block and skips the corner children by a branch. Not adopted.
