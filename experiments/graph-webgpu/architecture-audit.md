# How closely does WebGPU follow the original Cosmos?

At revision `93e23212`, a contributor changing a force can open the same folder and class in either engine. A contributor changing a link width follows two different paths. WebGL dispatches the edit to `Lines.updateWidth()`. On the next `render()`, WebGPU packs all point styles, rebuilds point order, packs every link and writes all three buffers. **Points and Lines update ownership is the largest remaining architectural difference.** [WebGL update dispatch](../../src/index.ts#L1927) · [WebGPU render](src/graph.ts#L113) · [WebGPU buffer writes](src/renderer.ts#L161)

## Differences an application can observe

Two focused comparisons used the real WebGL and WebGPU bundles on Apple M3 in Chrome.

- **Transition getters.** Two points and one link started with point radius 4 and link width 2. A linear, 1,000 ms transition targeted 20 and 10. With the same controlled clock, both engines reported progress 0.5 at 500 ms. WebGL's getters returned **12 and 6**, while WebGPU's returned **20 and 10** at both 0 ms and 500 ms. Both ended at 20 and 10. This probe measured the API values. [WebGL getters](../../src/index.ts#L1465) · [WebGPU getters](src/graph.ts#L281)
- **Non-finite friction, fixed after the audit.** A single gravity step with `NaN` friction previously turned all four coordinates of the two-point WebGPU fixture into `NaN`. Both engines now use the shared default of 0.85 at integration. On M3, the rebuilt packages returned identical positions for a gravity step and a paused right-button impulse at 0.85, `NaN`, both infinities, zero and −0.5. With gravity 0.25 the point at the origin stayed still and the second point moved from x = 2008 to x ≈ 2008.85 for all three non-finite inputs. [Reference regression](../../test/unbounded-space.test.ts#L1244) · [WebGPU regression](test/forces.test.ts#L22)

## Contributor experience and next changes

1. **Make the radius and width getters follow the displayed transition.** Turn the M3 midpoint probe into a paired regression. Add checks for disappearing geometry and stationary hover, and reuse the WebGL tracker contract for headless consumers. Keep the existing stories as the common input.
2. **Give Lines its own update first, then Points.** Start with `setLinkWidths()` followed by `render()`. Verify that a width-only update uploads zero point-style and point-order bytes and still draws and picks the new width. Exercise a point-only edit in the other direction. Keep the existing targeted highlight path, interrupted transitions and both Deck ownership modes working. [Narrow WebGL update](../../src/modules/Lines/index.ts#L597) · [WebGPU highlight path](src/renderer.ts#L196)
3. **Make the public API as readable in an editor.** Counting public instance method declarations with attached JSDoc gives Graph **84/84** in WebGL and **4/78** in WebGPU. For GraphSimulation the counts are **42/42** and **2/32**. These counts include methods marked internal. Carry over array layouts, units and the setter-to-render timing. Describe read freshness and the borrowed buffer lifetime in WebGPU's own terms. Expand multi-operation one-liners where ordering matters, and use one import convention for shared source. [WebGL setter](../../src/index.ts#L559) · [WebGPU setter](src/graph.ts#L251) · [Shared imports in Graph](src/graph.ts#L5) · [Shared imports in GraphSimulation](src/simulation.ts#L3)
4. **Then simplify the simulation coordinator.** Expose the ordered tick and share backend-independent rules such as the collision cutoff and initial position scaling. Keep backend-specific allocation, upload and disposal local. WebGPU constructs its common kernels even for a static scatterplot. Measure startup and first draw with simulation disabled and after enabling it before changing those lifetimes. [WebGL cutoff](../../src/modules/ForceCollision/index.ts#L31) · [WebGPU cutoff](src/modules/ForceCollision/index.ts#L40) · [WebGL scaling](../../src/modules/Points/index.ts#L3736) · [WebGPU scaling](src/simulation-data.ts#L5) · [Kernel creation](src/simulation-kernels.ts#L29)

**Point diameter is a separate design choice.** WebGPU draws instanced quads, which makes a larger limit possible. The candidate still uses the shared Store's 64 CSS-pixel limit. If the limit changes, agree on the footprint for drawing, picking and area selection together and check large points at both pixel ratios. [Store limit](../../src/modules/Store/index.ts#L8) · [Quad diameter](src/modules/Points/draw-points.wgsl#L26) · [Selection footprint](src/graph.ts#L626)

## Verification

The audit compared the authored engine TypeScript, shader and module organization, shared CPU components, Deck host boundary, package entries, public declarations, stories and tests. Typechecking the same `src/stories/**/*.ts` files against each built Graph declaration passed for WebGL. WebGPU reported exactly three errors, all for `getPointPositionsArray()`, in `far-point.ts`, `space-wall.ts` and `steady-state-motion.ts`. The Deck fixture is a separate consumer. Existing pixel and force comparisons establish behavior for their named fixtures.
